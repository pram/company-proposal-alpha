Review of technical specification v0.1

SLM Platform Plan

An assessment of the Hybrid Small Language Model Factory specification, the questions it leaves open, and a phased plan to build it with a very small team.

Specification dated 7 November 2026 Source: outline/slm_platform_technical_specification.md
planning-assumptions.yamlconfirmed with the founder
team: solo founder, or 1–2 engineers
firstProduct: model-deployment-kit
designPartner: none yet
factoryToday:
  tooling: Python scripts and notebooks
  compute: RunPod
  publishing: pushed to Hugging Face by hand  # no provenance captured

Verdict

The specification is technically sound and unusually disciplined for a first draft. It picks the right first milestone, a stable contract between creating a model and deploying it, and it treats evaluation as a condition of release.

Its main weakness is proportion, not technology. It describes a company with three products and a shared multi-customer platform. With one or two engineers and no design partner, about 80% of it should wait. The part built first should be chosen to learn from customers, not for architectural completeness.

Issues and recommended changes

Scope is far larger than the team

High impact

The specification covers ingestion, dataset generation, training orchestration, a registry, packaging, three runtimes, three deployment profiles, an API gateway, multi-tenancy, monitoring, remote management and an application layer. Each of these is a product in its own right.

Recommendation

Build the Deployment Kit as a single Python command-line tool. Run the Factory as a service you perform with your existing scripts, made reproducible but not yet automated. Defer the management platform, API gateway, multi-tenancy, remote management and AI Applications until a paying customer asks for them.

The Kit's commercial value is unproven

High impact

Serving an open-weights model is already easy. vllm serve, Ollama, Hugging Face Inference Endpoints, NVIDIA NIM, BentoML, KServe and hosted fine-tune-and-serve providers all cover parts of it. A tool that only generates a Docker Compose file for vLLM will not justify a purchase.

The defensible value is what those tools do not offer together:

  • A tested list of which model, runtime version and GPU combinations work, with evidence.
  • Signed, checksummed bundles that install on networks with no internet access.
  • Evaluation and performance results shipped with the package.
  • Provenance from source data to deployed model, when combined with the Factory.

These matter most to regulated and security-conscious buyers, who also need the most expensive features: offline bundles, signing and Kubernetes.

Recommendation

  • Treat the first three months as customer discovery plus MVP. Aim for one design partner before building Kubernetes support.
  • Build offline bundles, signing and the validation report earlier, in Phase 3. Push Helm later.
  • Make the first paid offer a done-for-you fine-tune: "we fine-tune a model on your data and deliver a tested, signed, installable package". This earns from the existing RunPod workflow, and every engagement adds to the compatibility list.

Two languages are too costly for a solo build

High impact

Section 14 proposes Java and Spring Boot for the platform API, Python for machine learning and JobRunr for jobs. Two stacks double the build pipelines, dependency management, deployment and context switching. Everything the MVP needs, including the Hugging Face client, safetensors inspection, vLLM and evaluation tools, is Python.

Recommendation

Use Python only until there is a team and a reason. Build the Kit as an importable library with a thin command-line layer. When the management platform arrives in Phase 5, expose the same library through FastAPI. The Java client in §7.2 can stay as generated documentation, since the API is OpenAI-compatible.

Don't build a registry, gateway or workflow engine yet

Medium impact

Section 19 asks whether to build or adopt each of these. For the MVP, none of them needs to exist as a service.

Check existing packaging standards first

Medium impact

The manifest in §7.3 is a reasonable start. Before freezing it, evaluate these:

  • OCI artifacts for model weights, pushed with ORAS or in the KitOps ModelKit format. Weights then live in any container registry, copy into isolated registries with standard tools, and are signed the same way as images. This could settle the storage, offline-install and signing decisions together.
  • Sigstore cosign for signing, syft for software bills of materials, trivy or grype for scanning, and SLSA-style provenance attestations.
  • Model cards or a CycloneDX ML-BOM for the provenance record.

Recommendation

Keep your own manifest as the deployment contract, and have it point to these standard artefacts rather than copy them.

Avoid custom runtime images in the MVP

Medium impact

Section 7.4 builds a custom Dockerfile on top of vllm/vllm-openai. The upstream image already contains the server.

Recommendation

Reference the upstream image by digest and pass configuration as arguments. This removes an image build, a registry and a patching obligation from the MVP. Fetching and verifying the weights can run in a separate init container.

Gaps the specification doesn't cover

GapWhy it matters
Base-model licences when redistributingMerged models inherit the base licence. Some carry attribution, naming and usage conditions (for example the Llama community licence). Gemma has its own terms. Many Qwen models are Apache 2.0, but not all. The compatibility list needs a licence field that can block packaging.
Terms of the model that generates synthetic dataSeveral commercial model providers restrict using their outputs to train competing models. Check before building dataset generation on one (§4.3).
Ownership of fine-tuned weightsWho owns the adapter, and can lessons be reused across customers? This belongs in the contract before the first Factory engagement.
Structured outputThe banking example returns JSON. vLLM can force output to match a JSON schema, which makes valid output close to certain. It should be a manifest option and something the evaluation measures.
Serving many adapters on one modelvLLM can serve many customers' LoRA adapters on one base model. For managed hosting this is the main cost lever and the practical answer to the multi-tenancy question in §19. Merge by default for customer-installed packages.
Cost of GPUs for testingValidation needs real GPUs. Budget for on-demand GPUs per run and keep the supported list small.
Patches and supportShipped packages pin vLLM versions that will get security fixes. Decide support windows and how customers receive updated bundles.
RegulationIf customers use models for decisions such as creditworthiness, EU AI Act high-risk obligations may apply to them, and indirectly to you as a supplier. Get advice before selling into banking.
Commercial modelPricing per package, per model, by subscription or per token changes what must be metered and built.
Estimating hardwareThis can be computed: weight size, plus KV cache (2 × layers × KV heads × head size × bytes × context × concurrent requests), plus runtime overhead. Then confirm it with a measured benchmark.

Smaller points

  • Produce the evaluation report as Markdown or HTML plus JSON instead of PDF (§7.2). A PDF can be rendered later.
  • Choose the real domain for apiVersion: slm.example.com/v1 early. It is hard to change once packages ship.
  • MVP criterion 9 needs a definition of "supported GPU host": the GPUs, driver versions and container toolkit versions.
  • The Phase 1 exit criterion should include a published, versioned JSON Schema for the manifest, so the contract can be checked by machine.
  • The specification has no business success measures, such as the time to package a new model or the number of tested combinations. Add them so progress is measurable.

Part B

Open questions

Numbered so the plan can refer to them. A blue tag marks a question that must be answered before that phase starts.

Business and commercial

  1. 1
    Blocks Phase 0

    Which buyer segment comes first: regulated enterprises running on their own hardware, mid-market firms happy with managed hosting, or software vendors embedding models? This decides whether offline and Kubernetes support or managed hosting comes first.

  2. 2

    What is the pricing model: a licence per package, a subscription with updates, a fee per fine-tuning engagement, or managed hosting priced per token or per instance?

  3. 3

    Is the Kit open source, with paid tested packages and support, or proprietary?

    An open-source tool is a credible way to reach users in this market, but it changes what you can charge for.

  4. 4

    What is the budget for GPU time for development, testing and demos?

  5. 5

    When do you want the first revenue?

Legal and data

  1. 6
    Blocks first Factory engagement

    Who owns fine-tuned weights, datasets and synthetic data? What reuse rights do you keep?

  2. 7

    Which model or models will generate synthetic data, and do their terms allow it?

  3. 8

    Where may customer data be processed? Does RunPod meet your target customers' security and data-residency requirements?

  4. 9

    Will you pursue SOC 2 or ISO 27001, and when?

Technical

  1. 10
    Blocks Phase 2

    Which 2–3 model families and sizes, and which GPUs, will the first version support? For example, one 24 GB class (L4, A10G) and one 80 GB class (A100, H100).

  2. 11
    Blocks Phase 1

    Will model weights be stored as OCI artifacts (ORAS or KitOps), or stay on Hugging Face and S3?

    Recommended: a one-week test in Phase 1.

  3. 12

    Does the MVP need the Ollama and llama.cpp (GGUF) profile, or only vLLM?

    Recommended: vLLM only until a customer needs CPU or edge deployment.

  4. 13

    Should the first package serve LoRA adapters directly, or merged models only?

    Recommended: merged models only for customer-installed packages.

  5. 14

    What does the current training workflow use (Unsloth, Axolotl, TRL or custom code), and which settings are already recorded?

  6. 15

    Which domain and name will the manifest's apiVersion use?

Part C

Implementation plan

Ground rules

  • One language, one repository, one command-line tool. Python 3.12 with uv, Typer, Pydantic 2, Jinja2 templates and pytest.
  • Library first. All logic lives in slm_kit, so the later web service calls the same code.
  • Compatibility as data. The compatibility list and GPU profiles are tested YAML files, not code branches.
  • Every phase ends in a demo you can show a prospective customer.
  • Customer discovery runs alongside engineering through Phases 0–3.

Timeline

Assumes one full-time engineer. With two, Phases 2 and 3 overlap and the plan shortens by about a third.

Phase 0 · Foundations and discovery

weeks 0–2

Engineering

  1. Create the repository (layout below), automated checks in GitHub Actions (lint, type checks, unit tests), pre-commit hooks, and a licence decision for the code.
  2. Start docs/adr/ and record the first decisions: Python only, the manifest as the contract, vLLM as the first runtime, no custom runtime image.
  3. Set up accounts: a Hugging Face organisation with private repos, an S3-compatible bucket, a RunPod API key in a secrets manager, and a container registry.
  4. Choose the first support list (question 10). A good start: two or three current open-weights families with permissive licences at 1–8B parameters, on one 24 GB GPU class and one 80 GB class.

Business

  1. List 30 target companies in one segment and hold 10–15 discovery conversations. Test the offer: a tested, signed, installable model package, with optional fine-tuning on their data.
  2. Get legal advice on redistributing base-model licences, synthetic-data terms and a standard data and IP clause (questions 6–7).

Phase 1 · Standardise the model output

weeks 2–5
  1. Manifest schema v1alpha1 as Pydantic models, exported to JSON Schema in schemas/. It holds the fields from §5.1 and §7.3, plus licence, chat template, structured-output settings, provenance (dataset, training run, evaluation) and a list of artefacts with SHA-256 checksums.
  2. Source resolvers for Hugging Face (turn a branch or tag into a commit hash, fetch with a token from a secret), local directories and S3.
  3. slm-kit inspect reads config.json, the safetensors headers (parameter count and dtype without loading weights), the tokenizer and chat template, the licence from the model card, and file checksums. It writes a draft manifest.
  4. Factory hook. Change the RunPod scripts to write provenance.json (base model and revision, dataset hash, settings, seed, library versions, GPU type, timings) and push it with the model.
  5. One-week test of OCI artifacts for weights (question 11). Push a model with ORAS or KitOps, pull it on an isolated network, sign it with cosign, and record the decision.
Exit
Every existing model in your Hugging Face organisation produces a valid manifest, and new training runs record provenance automatically.

Phase 2 · Deployment CLI MVP

weeks 5–10
  1. Compatibility list for the chosen vLLM version: supported architectures, dtypes, quantisation, LoRA support, minimum GPU generation and known issues. Each check returns supported, unsupported with a reason, or needs conversion with the steps.
  2. Hardware estimator covering weights, KV cache and overhead per GPU profile. It recommends context length, GPU memory share and concurrent requests, and labels them as estimates until Phase 3 measures them.
  3. slm-kit package generates:
    • manifest.yaml and runtime-config.yaml
    • docker-compose.yaml with the upstream vLLM image by digest, an init container that fetches weights and checks their checksums, a reverse proxy with TLS and API keys, health checks on vLLM's /health, a restart policy, a read-only model volume, GPU reservations and log settings. The model port is never exposed outside the internal network.
    • .env.example, an OpenAPI description of the supported part of the OpenAI chat API, and curl, Python and Java examples.
    • Installation, configuration, operations and troubleshooting guides.
    • checksums.sha256
  4. slm-kit install --target docker checks the NVIDIA driver, container toolkit, GPU memory and disk space, then starts the stack.
  5. slm-kit validate starts the package on a RunPod GPU or locally, waits until it is ready, and runs smoke tests: a chat completion, streaming, schema-forced JSON if configured, and a request without a key that must be rejected. Then it shuts everything down and explains any failure.
  6. Golden-file tests for generated output, and a nightly GPU job that packages and validates every combination on the list.
Exit
A supported model is packaged and runs on a supported GPU host with no manual edits, and all 15 MVP criteria in §18 pass.
Demo
From a Hugging Face repo to a tested package serving an authenticated API in under 15 minutes.

Phase 3 · Evidence, integrity and offline install

weeks 10–14

Brings the supply-chain items from §7.7 forward, because they set the Kit apart.

  1. Performance benchmark: latency percentiles, throughput and tokens per second at several concurrency levels, and peak GPU memory. Saved in benchmark.json and used to correct the estimator.
  2. Task evaluation on a customer or Factory evaluation set: exact match, JSON validity, per-field accuracy and F1, compared with the base model. Thresholds live in the manifest, and packaging fails if they are missed.
  3. Evaluation report in Markdown or HTML plus JSON, covering intended use, limitations, method, results, baseline and approval status.
  4. Supply chain: a software bill of materials (syft), an image scan (trivy or grype), cosign signatures for the bundle and image digests, and slm-kit verify.
  5. slm-kit bundle --offline produces one archive with saved images, weights, signatures and an installer, tested on a host with no outbound network.
Exit
Every package ships with reproducible evidence and can be installed and verified offline.
Demo
The version to show design partners.

Phase 4 · Kubernetes

weeks 14–20, only with a partner

Start only when a design partner needs it. Otherwise, extend the compatibility list, add the GGUF and Ollama profile, or invest in the Factory.

  1. A Helm chart with a values schema, GPU requests, node selectors and tolerations, probes, network policies, pod security settings, secret references, and weight loading from a volume or object storage.
  2. Testing on k3s or kind with a GPU node, then on the partner's platform (EKS, AKS, GKE or OpenShift).
  3. Rollback by Helm revision and a documented upgrade procedure.
Exit
The partner installs a tested package into their own cluster.

Phase 5 and beyond · Platform, automation, applications

once the Kit has paying users
  • Management service: FastAPI around slm_kit, Postgres for customers, projects, models, packages and deployments, object storage, and the workflow engine chosen at that point.
  • Factory automation: ingestion, dataset generation, quality checks, training on RunPod, an evaluation gate, registration and packaging, each a retryable step with human approval where needed (§15).
  • Managed hosting: many adapters per base model on vLLM, behind a gateway with usage metering.
  • Web interface, then the first AI application, chosen from problems seen in Factory engagements.

Factory track

alongside Phases 1–3

Keep the Factory as a service. Make it reproducible, not automated.

  1. Move scripts and notebooks into factory/ as scripts driven by config files, with no hidden notebook state. Pin library versions and set seeds.
  2. Add dataset hashing, train, validation and test splits with leakage checks, and a record of where each synthetic example came from (§4.3).
  3. Have every run write provenance.json and push to a private Hugging Face repo with a manifest, so its output goes straight into slm-kit package.
  4. Hold back an evaluation set for each engagement. It becomes the input to Phase 3's task evaluation.
